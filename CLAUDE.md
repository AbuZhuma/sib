# Asiba

Настольное приложение мониторинга Linux-серверов на Rust. ТЗ — `docs/TZ-v1.md`, архитектура — `docs/ARCHITECTURE.md`, журнал решений — `docs/DECISIONS.md`. Перед любой задачей читай ТЗ в части, которую затрагиваешь.

## Правила кода

### Без комментариев
- В коде комментариев нет. Ни `//`, ни `/* */`, ни doc-комментариев `///`.
- Если что-то требует пояснения — переименуй, вынеси в функцию с говорящим именем или упрости. Если после этого всё ещё непонятно — это место в `docs/`, а не в коде.
- Исключение: `#[allow(...)]` с обоснованием в атрибуте `reason = "..."` и `TODO` запрещены — вместо TODO заводи задачу.

### Чистота и размер
- Файл — не более 300 строк. Приблизился — дели по ответственности, а не по номеру.
- Функция — не более 40 строк, не более 4 параметров. Больше — структура-параметр или разбиение.
- Один файл — одна ответственность. Один модуль — одна папка с `mod.rs` только для `pub use` и объявлений.
- Никакой вложенности глубже 3 уровней. Ранние возвраты вместо `else`-лестниц.
- Имена: полные слова, без сокращений кроме общепринятых (`id`, `cpu`, `ssh`, `io`). Булевы — `is_`/`has_`/`can_`. Функции — глагол. Типы — существительное.
- Никаких `unwrap()` и `expect()` вне тестов. Все ошибки — типизированные через `thiserror` в библиотечных крейтах; `anyhow` только в `asiba-app`.
- Никаких `panic!`, `todo!`, `unimplemented!` в основном коде.
- `clone()` только когда действительно нужен; каждое `Arc<Mutex>` обосновано в `DECISIONS.md` или заменено каналом.
- Магические числа и строки — в именованные константы в начале файла или в конфигурации.
- `unsafe` запрещён без записи в `DECISIONS.md`.

### Архитектура
- Направление зависимостей: `core ← transport, storage, config ← modules ← incidents ← docgen, alerts ← ai ← engine ← ui ← app`. Обратные зависимости запрещены.
- `asiba-core` не зависит ни от SSH, ни от egui, ни от SQLite.
- Новый источник данных — всегда новый модуль по `docs/MODULE_GUIDE.md`, никогда не дописывание существующего.
- Модуль обязан корректно отвечать `Unavailable`, если данных на сервере нет. UI никогда не показывает недоступный модуль.
- UI не выполняет сеть и не блокируется: только читает состояние и отправляет команды в канал.
- Парсеры вывода команд — чистые функции `&str -> Result<T>`, без транспорта внутри, с тестами на фикстурах.
- Каждая команда, которую модуль выполняет на сервере, перечислена в `docs/MODULE_GUIDE.md` в разделе модуля.
- Стиль UI — только через токены темы в `asiba-ui/src/theme/`. Цвета, радиусы, отступы в компонентах не пишутся напрямую.

### Тесты
- Каждый парсер — тесты на реальных примерах вывода в `fixtures/<module>/`.
- Логика без IO (агрегации, пороги, аномалии, docgen) — юнит-тесты рядом с кодом в `#[cfg(test)] mod tests`.
- Тесты называются по формуле `<что>_<условие>_<ожидание>`.

### Процесс
- Перед сдачей: `cargo fmt`, `cargo clippy --all-targets -- -D warnings`, `cargo test`. Всё зелёное.
- Один коммит — одно логическое изменение. Сообщение — императив, английский, до 72 символов в заголовке.
- Архитектурное решение (выбор крейта, изменение трейта, новый крейт) — запись в `docs/DECISIONS.md`: контекст, варианты, выбор, причина.
- Зависимости добавляются в корневой `[workspace.dependencies]` и подключаются через `workspace = true`. Версии зафиксированы.
- Не добавлять функциональность сверх задачи. Не переписывать соседний код «заодно».

## Команды
```
cargo build                         сборка
cargo run -p asiba-app              запуск
cargo test --workspace              тесты
cargo clippy --all-targets -- -D warnings
```
