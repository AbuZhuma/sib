# Журнал архитектурных решений

Формат: дата, контекст, варианты, выбор, причина.

## 2026-09-14 — UI на egui

Контекст: нужен настольный Linux-клиент с живыми графиками и полностью кастомным серым стилем.
Варианты: egui/eframe, iced, Tauri (веб-фронт), GTK4-rs.
Выбор: eframe/egui 0.36.
Причина: immediate mode без затрат на синхронизацию состояния, стиль задаётся токенами полностью, есть `egui_plot` и `walkers` для карты. Tauri тянет веб-стек, iced медленнее в разработке.

## 2026-09-14 — SSH через russh

Варианты: russh, ssh2 (libssh2), openssh CLI через процесс.
Выбор: russh 0.63.
Причина: чистый Rust, async, ключи/пароль/agent/certificate, `known_hosts` из коробки. CLI-обёртка не даёт мультиплексирования каналов в одной сессии.

## 2026-09-14 — Отдельный крейт asiba-engine

Контекст: в ТЗ логика воркеров была внутри `asiba-app`.
Выбор: вынести в `asiba-engine`.
Причина: жизненный цикл соединений, расписание и команды — это ядро приложения с тестами, а не «склейка». `asiba-app` остаётся точкой входа на 40 строк.

## 2026-09-14 — Снимок модуля как `Arc<dyn ModuleData>`

Варианты: enum со всеми типами данных в core; generic `Snapshot<T>`; type-erased `Arc<dyn Any>`.
Выбор: `Arc<dyn ModuleData>` с `downcast::<T>()`.
Причина: core не должен знать типы модулей; enum ломает правило «новый модуль = новая папка». Downcast делается только в UI-представлении модуля.

## 2026-09-14 — `Arc<RwLock<AppState>>` вместо каналов для состояния

Причина: UI читает всё состояние на каждом кадре; передавать снимки по каналу значило бы копировать всё состояние 60 раз в секунду. Запись — короткая, без await под блокировкой. Команды UI → движок идут каналом.

## 2026-09-14 — `Arc<Mutex<Option<HostKeyVerdict>>>` в SSH-обработчике

Причина: `russh::client::Handler::check_server_key` возвращает только `bool`; отпечаток ключа надо вынести наружу, чтобы показать пользователю. Обработчик и вызывающий код живут в разных задачах, канал на одно значение избыточен.

## 2026-09-14 — Секреты в keyring без fallback (этап 1)

Контекст: ТЗ предусматривает зашифрованный файл как запасной вариант.
Выбор: пока только keyring (`secret-service`); при ошибке сервер запускается без секретов и в UI показывается предупреждение.
Причина: fallback требует мастер-пароль и UI для него — переносится на этап 4 (безопасность).

## 2026-09-14 — Режим входа «авто» без разбора `~/.ssh/config`

Выбор: авто = ssh-agent → `~/.ssh/id_ed25519`, `id_ecdsa`, `id_rsa` → пароль, если задан.
Причина: разбор `ssh_config` (алиасы, `IdentityFile`, `ProxyJump`) — отдельная задача; заведена на этап 2.

## 2026-09-14 — Скриншот по переменной окружения

Контекст: проверить UI без ручных кликов под Wayland нельзя (портал скриншотов требует подтверждения).
Выбор: `ASIBA_SCREENSHOT=path [ASIBA_SCREENSHOT_DELAY=сек]` — приложение сохраняет кадр и закрывается. Код в `asiba-ui/src/devtools.rs`.

## 2026-09-14 — Скорости через предыдущий снимок, а не через `sleep` в скрипте

Контекст: cpu %, байты/с и IOPS требуют двух замеров счётчиков.
Варианты: скрипт с `sleep 1` между двумя `cat`; состояние на сервер внутри модуля (`Mutex<HashMap<ServerId, _>>`); передать модулю предыдущий снимок.
Выбор: `CollectContext { previous }`.
Причина: модуль остаётся без состояния и без знания о серверах; нет секунды простоя SSH-канала на каждый сбор.

## 2026-09-14 — Одна задача на модуль вместо общего планировщика

Контекст: Fast-модули (cpu, memory, disk, network, processes) собираются каждые 2 с; последовательный сбор по одному каналу не укладывался бы в интервал.
Выбор: после `detect` воркер запускает `JoinSet` задач, по одной на доступный модуль, все на одной SSH-сессии (мультиплексирование каналов). Потеря соединения — через `watch`-канал; повторный `detect` раз в 10 минут перезапускает набор.

## 2026-09-14 — История: кольцо в памяти + SQLite в отдельном потоке

Выбор: `ServerState.series` хранит 900 последних точек на метрику для графиков; `asiba-storage` пишет те же сэмплы батчами раз в 5 с из своего потока (`std::thread`, rusqlite не async). Раз в час: сырые > 48 ч сворачиваются в поминутные (avg/min/max), поминутные > 30 дней — в почасовые, почасовые > 1 года удаляются.
Причина: UI не должен ходить в SQLite на каждом кадре; чтение длинных диапазонов из базы появится вместе с переключателем окна графика.

## 2026-09-14 — `~/.ssh/config` через `ssh2-config`

Выбор: перед подключением хост из формы прогоняется через `~/.ssh/config`: `HostName`, `IdentityFile` учитываются; `Port` и `User` из формы имеют приоритет (форма их требует явно). `ProxyJump` из ssh_config не читается — jump host задаётся в форме.

## 2026-09-14 — Пинг из движка, а не модуль

Причина: пинг измеряется с локальной машины (TCP-connect на SSH-порт, ICMP требует прав), транспорт не нужен; работает и когда сервер offline — это и есть индикатор доступности.

## 2026-09-14 — `asiba-docgen` зависит от `asiba-modules`

Контекст: в ТЗ порядок был `core ← docgen ← modules`. Но файл сервера рендерит данные конкретных модулей (проекты, docker, порты).
Выбор: `core ← modules ← docgen ← engine`. Движок вызывает docgen после снимков модулей-триггеров (system, projects, services, docker, ports), не чаще раза в минуту и только если тело файла изменилось. Ручной блок `notes` сохраняется.

## 2026-09-14 — `Module::query` для данных по требованию

Контекст: логи контейнера и журнал юнита нельзя собирать постоянно.
Варианты: отдельный трейт; команды-строки из UI напрямую в транспорт; метод трейта с default-реализацией «не поддерживается».
Выбор: `async fn query(&self, transport, &QueryRequest) -> QueryResponse`. UI не знает команд — только `kind` и `target`; команду формирует модуль.

## 2026-09-14 — `Arc<Mutex<Option<Arc<dyn Transport>>>>` в воркере

Причина: запрос по требованию должен идти по живой SSH-сессии сервера, а она принадлежит задаче воркера. Слот заполняется при подключении и очищается при потере; движок берёт клон `Arc` под коротким локом. Канал команд в воркер был бы вторым каналом с тем же содержимым.

## 2026-09-14 — Docker через Go-шаблоны, а не `--format json`

Причина: `podman` эмулирует CLI docker, но JSON у `ps`/`stats` другой. Явные `--format '{{.Field}}\t…'` одинаковы для обоих. `docker stats --no-stream` собирается раз в 20 с вместе с остальным (не Fast) — секундная задержка команды не мешает.

## 2026-09-14 — Файрвол только через sudo

Причина: `nft`/`iptables`/`ufw` без root не читаются. Без sudo модуль `ports` работает в режиме `Partial`, доступность снаружи всё равно проверяется TCP-connect'ом — это и есть фактический ответ.

## 2026-09-14 — Действия через `Module::perform`

Контекст: бан IP, kill, restart юнита/контейнера — единственные команды записи на сервере (ТЗ §8).
Варианты: отдельный трейт `Actor`; команды-строки из UI; метод трейта с default «не поддерживается» (как `query`).
Выбор: `fn actions() -> &[ActionSpec]` и `async fn perform(transport, &ActionRequest) -> ActionOutcome`. Спеки (`kind`, заголовок, `Danger`) объявлены константами модуля — UI ссылается на них и не знает команд. Цели валидируются модулем (IP парсится, PID — число > 1, имена юнитов/контейнеров — только `[A-Za-z0-9.-_@:]`), чтобы в shell не попало ничего лишнего. Движок пишет каждое действие в SQLite (`actions`) и в `AppState.actions`; UI показывает подтверждение с вводом имени сервера, если `Danger::High` или окружение сервера — production.

## 2026-09-14 — Порядок бэкендов бана

Выбор: fail2ban (если есть джейл) → nftables → iptables → ufw. Срок бана поддерживает только nftables (элемент set с `timeout`); остальные — постоянный, об этом говорит сообщение результата. Приложение создаёт собственную таблицу `inet asiba` с set'ами `bans`/`bans6` и цепочку `ASIBA` в iptables, чтобы не трогать чужие правила и уметь перечислить свои баны.

## 2026-09-14 — Крейт `asiba-alerts` и типы алертов в `asiba-core`

Контекст: правила алертов хранятся в `config.toml` (`asiba-config`), а вычисляются в движке; `config` не может зависеть от `alerts`.
Выбор: типы `AlertRule`, `Alert`, `Condition` — в `asiba-core` (данные + serde), логика (встроенные правила, оценка, базовая линия, уведомления) — в `asiba-alerts`, движок раз в 5 с прогоняет `Evaluator::evaluate` над `AppState` под write-lock. Пользовательские правила с тем же `id`, что у встроенного, замещают его.

## 2026-09-14 — Базовая линия: EWMA вместо профиля по времени суток

Контекст: ТЗ §5.12 хочет среднее и отклонение за 24 ч с учётом времени суток. Для этого нужна история из SQLite и профиль на каждый час.
Выбор в v1: экспоненциально взвешенные среднее и дисперсия (полураспад ~1 ч при оценке раз в 5 с), прогрев 10 мин, порог 4σ, минимальная σ — 5 % от среднего и не меньше 1. Аномалия должна держаться 60 с. Профиль по времени суток — задел на потом; ключи метрик перечислены в `evaluator.rs`.

## 2026-09-14 — Уведомления через `notify-rust`

Причина: D-Bus-уведомления на Linux без обвязки; отправляются только для warning/critical и только при поднятии алерта (не при обновлении). Ошибка отправки логируется и не влияет на работу.

## 2026-09-14 — Геолокация через ip-api.com из движка

Контекст: положение сервера нужно для карты; внешний сервис может быть недоступен.
Выбор: `asiba-engine::geo` — при старте воркера: ручные координаты из `[location]` в `servers/<name>.toml` → кеш `~/.cache/asiba/geo.json` (30 дней) → HTTP `ip-api.com/json/<ip>` (`ureq`, blocking в `spawn_blocking`). Хост резолвится через DNS; частный или loopback-адрес считается «этой машиной» — берётся собственное положение (запрос без IP). Положение локальной машины хранится в `AppState.self_location`. Файл кеша защищён глобальным `Mutex`, потому что несколько воркеров резолвятся параллельно. Сервис меняется в одном месте (`fetch`).

## 2026-09-14 — Карта на `walkers`

Причина: `walkers 0.59` собран под egui 0.36, умеет OSM-тайлы с HTTP-кешем на диске (`~/.cache/asiba/tiles`) и плагины для собственной отрисовки. Маркеры, линии от локальной машины и подписи пинга рисуются плагином `Markers`; клик по маркеру возвращает `ServerId` через временные данные egui. Один `MapState` (тайлы + память карты) живёт в приложении и используется и на странице «Карта», и в мини-карте на главной. Без интернета тайлов нет, но точки и линии рисуются.

## 2026-09-14 — Страны атакующих IP пакетным запросом

Причина: атакующих адресов много, лимит ip-api — 45 запросов в минуту. Задача `engine::peers` раз в 30 с собирает неизвестные публичные IP из `security.attackers` и `anomalies.top_peers` (до 100), делает один `POST /batch`, результат — в `AppState.ip_countries` и `~/.cache/asiba/countries.json`. UI получает карту через `ViewShared`, чтобы модульные представления не зависели от `AppState`.

## 2026-09-15 — Секции в asiba-docgen и второй файл для модели

Контекст: план ИИ-анализа (`docs/AI-PLAN.md`) требует давать модели только нужные части данных и держать полный файл в бюджете контекста; файл для человека должен содержать всё, что показывает программа.
Варианты: один markdown-файл, который модель читает целиком; JSON-дамп состояния; набор секций с двумя рендерами.
Выбор: трейт `Section { id, is_available, human, llm }` и `SectionId`; два файла `<name>.md` и `<name>.llm.md`; `render_llm_sections` для подмножества.
Причина: секции — единица выбора контекста для плейбуков инцидентов; `key: value` на английском компактнее таблиц и лучше читается малыми моделями, чем JSON; человек получает полный русский markdown без ограничений на объём.

## 2026-09-15 — Крейт asiba-incidents

Контекст: файл сервера, UI и будущие ЛЛМ-триггеры должны одинаково понимать «что плохо». Детекторы в `asiba-alerts` недоступны `asiba-docgen` (соседние крейты), а дублировать логику в двух местах нельзя.
Варианты: детекторы внутри `asiba-alerts` + копия в docgen; детекторы в `asiba-modules`; отдельный крейт между modules и docgen/alerts.
Выбор: `asiba-incidents` (`modules ← incidents ← docgen, alerts`), типы `Incident`, `IncidentDraft`, `IncidentKind` в `asiba-core`.
Причина: одна реализация для секции findings, списка инцидентов в UI и плейбуков модели; новый детектор — один файл и одна строка в списке.

## 2026-09-15 — Крейт asiba-ai: Gemini API вместо локальной модели

Контекст: первая версия аудита запускала локальную `llama-server` с Qwen3-4B (см. историю git до этого решения). На реальной машине без GPU разбор одного инцидента занимал ~6 минут (29 ток/с на промпт, ~2 ток/с генерация при занятой памяти), а установка требовала 2.3 ГБ модели и ~3 ГБ RAM. Пользователь решил отказаться от локальной модели.
Варианты: оставить локальную модель как опцию; Gemini API; OpenAI-совместимый API с выбором провайдера.
Выбор: крейт `asiba-ai` с трейтом `Backend` и единственной реализацией `Gemini` (REST `generateContent`, модель по умолчанию `gemini-2.5-flash`). ИИ выключен по умолчанию; включается только явным согласием (`AiConfig.consent`) и ключом API в настройках. Без согласия крейт не делает ни одного сетевого запроса. Локальный бэкенд, установщик и связанные настройки удалены полностью.
Причина: ответ за секунды вместо минут, качество разбора существенно выше, контекст 1M токенов позволяет отдавать логи целиком. Отправка данных наружу — осознанный выбор пользователя, зафиксированный галочкой; текст согласия перечисляет, что именно отправляется.

## 2026-09-15 — Модуль projects удалён

Контекст: модуль `projects` сканировал диск в поисках репозиториев и compose-файлов и связывал с ними контейнеры, юниты, процессы и порты; вкладка «Проекты», секция docgen и плейбуки ИИ опирались на него.
Варианты: оставить как есть; оставить только связку процессов с compose-проектами; удалить целиком.
Выбор: удалить целиком - модуль, вкладку, секцию `projects` в docgen, упоминания в плейбуках и текстах. Compose-группировка контейнеров остаётся внутри модуля `docker` (label `com.docker.compose.project`).
Причина: пользователь решил, что сущность «проект» не нужна: то же самое видно на вкладках Docker, Сервисы и Процессы, а сканирование диска - самый тяжёлый сбор из всех модулей.

## 2026-09-15 — Подгрузка истории через цикл сбора модуля

Контекст: журнал на вкладке «Логи» должен листаться бесконечно, а снимок модуля живёт в цикле сбора воркера (`previous` в `collect::run`).
Варианты: UI хранит догруженные страницы отдельно (запрос через `Module::query`); движок вызывает модуль вне цикла и пишет снимок в состояние; запрос передаётся в сам цикл сбора.
Выбор: `Module::backfill(transport, context)` в трейте, `Command::Backfill` и `tokio::sync::broadcast<ModuleId>` в `WorkerContext`; цикл `collect::run` ждёт либо тик, либо свой `ModuleId` и подменяет `previous` результатом.
Причина: снимок модуля - единственный источник данных для UI, docgen и инцидентов, дублировать его в UI нельзя; вызов вне цикла гоняется с очередным `collect` и терял бы свежие записи или догруженные. Broadcast вместо канала на модуль - один отправитель в записи воркера, каждый цикл фильтрует свой id.

## 2026-09-15 — Несколько провайдеров ИИ, анализ по разделам и сводка по парку

Контекст: пользователь хочет выбирать провайдера (GPT, Gemini, Claude и другие), видеть сводку по всем серверам при каждом запуске, разбор каждого инцидента на главной и анализ каждого раздела на вкладках сервера.
Варианты: один провайдер; свой трейт под каждого; OpenAI-совместимый протокол для всех.
Выбор: трейт `Backend` с тремя реализациями (Gemini, OpenAI/совместимые по `base_url`, Anthropic) и `AiProvider` в конфиге. Отчёты адресуются `AuditTarget` (сервер или парк) и `AuditScope` (Full, Incident, Section{key}); последний отчёт по паре target+scope показывается в блоке `ai_block`. Блок раздела запрашивает анализ один раз за сессию при первом открытии вкладки, дальше — по кнопке; сводка по парку — при запуске после первого сбора и по кнопке; полный аудит — только по кнопке.
Причина: единый протокол не покрывает Gemini и Anthropic без адаптеров, а три небольших реализации дешевле обёртки; автозапросы ограничены (раз за сессию на раздел, кулдаун на инцидент), чтобы расходы на API были предсказуемы.

## 2026-09-15 — Модуль git отдельно от deploy

Контекст: пользователь хочет видеть на сервере все git-репозитории целиком - ветки, remote, незакоммиченные файлы, историю коммитов. В модуле `deploy` git был одним из адаптеров и давал по 5 коммитов на репозиторий как «деплои».
Варианты: расширить git-адаптер внутри `deploy`; отдельный модуль `git` и убрать git из `deploy`; заменить `deploy` целиком на `git`.
Выбор: отдельный модуль `git` (вкладка «Git», расписание Normal, запрос `history <path>` для полной истории) и удаление git-адаптера из `deploy`; compose, systemd, лог-файлы и CI runner в `deploy` остаются.

## 2026-09-17 — Файловый менеджер как OnDemand-модуль поверх запросов и действий

Контекст: нужен просмотр всей файловой системы сервера с редактированием файлов, правами и удалением, при этом без нагрузки на сервер.
Варианты: периодический сбор дерева (как остальные модули); отдельный канал в транспорте (SFTP через russh); модуль без сбора - запросы `list`/`read` и действия `write`/`chmod`/`chown`/`delete` через существующие `Module::query` и `Module::perform`.

После успешного действия приложение само перезапрашивает родительскую папку и файл.
Причина: SFTP - отдельный протокол с собственной обработкой ошибок и sudo (через SFTP root не получить), а одной команды `find` на раскрытие папки хватает; периодический сбор дерева - как раз та нагрузка, которой нужно избежать. Текст как транспорт результата - компромисс: `QueryResponse` не имеет структурированного поля, а вводить его ради одного модуля было бы шире задачи. Содержимое файла едет в команде (`printf '%s' '...'`), поэтому размер ограничен 200 КБ - это ниже лимита пакета OpenSSH (256 КБ) с запасом на экранирование.
