# ИИ-анализ в Asiba (Gemini)

Цель: приложение само готовит для языковой модели ровно те данные, которые нужны, вызывает её по каждому негативному событию и по запросу, а результат показывает как аудит. Модель — Google Gemini по API; включается только явным согласием пользователя.

## Принципы

1. **Детерминированный анализ делает Asiba, а не модель.** Проверки безопасности, аномалии, алерты, упавшие юниты и деплои — это код с тестами (`asiba-incidents`). Модель получает факты и готовые выводы, её работа — связать их, расставить приоритеты, объяснить причину и предложить шаги.
2. **Контекст собирается из секций.** Все данные о сервере описаны как набор секций с идентификаторами (`asiba-docgen`). Полный файл — это все секции; контекст для инцидента — только нужные. Новая секция = новый файл, регистрация в списке.
3. **Каждый негатив — инцидент.** Единый тип `Incident` в `asiba-core`. Детекторы — маленькие модули с общим трейтом. Новая причина для вызова модели = новый детектор и (при необходимости) плейбук.
4. **Плейбук связывает инцидент с моделью.** Для каждого вида инцидента: какие секции дать, какие данные дополнительно запросить с сервера (логи контейнера, journalctl юнита), какую задачу поставить.
5. **Ничего не уходит без согласия.** По умолчанию ИИ выключен. В настройках пользователь ставит галочку с текстом, что именно будет отправляться в Gemini API, и указывает ключ. Пока `consent` не стоит, `asiba-ai` не делает сетевых запросов.
6. **Модель не блокирует UI и сбор данных.** Один воркер, очередь, один запрос за раз, кулдаун на повторные инциденты (по умолчанию 30 мин на `сервер:вид:объект`).

## Что отправляется

Только текст, собранный из секций `<имя>.llm.md` по плейбуку инцидента (или все секции для полного аудита), плюс вывод запросов к серверу (`docker logs`, `journalctl -u`). Пароли и ключи в этих данных не участвуют. Список секций: findings, description, system, resources, alerts, security, anomalies, services, docker, deploy, projects, processes, ports, users, updates, logs, gpu, actions, events.

## Модель и API

- Бэкенд: `asiba-ai::Gemini`, REST `generateContent`, ключ в заголовке `x-goog-api-key`. Модель по умолчанию `gemini-2.5-flash`, меняется в настройках.
- Лимит контекста задаётся в настройках (по умолчанию 60 000 токенов); секции режутся по приоритету, если не влезают.
- Ответ на русском, фиксированная структура: Summary / Root cause / Critical / Recommended / Notes, с ссылками на строки данных.

## Плейбуки

- контейнер упал / unhealthy → `docker logs`, секции docker, projects, resources, deploy, events;
- юнит упал → `journalctl -u`, секции services, logs, resources, projects, events;
- деплой упал → deploy (с хвостом лога), projects, docker, services, logs;
- аномалия / брутфорс → anomalies, security, ports, resources, events;
- проверка безопасности / обновления → security, users, ports, updates;
- ресурсы (алерты, диск, память, часы, ошибки модуля) → resources, processes, docker, services, logs;
- полный аудит → все секции, findings первым.

## Поток

1. Цикл алертов открывает инцидент (`asiba-incidents::reconcile`).
2. Если ИИ включён и `auto_audit`, движок ставит задание `Audit { scope: Incident }` в очередь воркера (`engine/src/ai/`). Кнопки «разобрать» и «Полный аудит» ставят задания вручную.
3. Воркер собирает контекст (`context::prepare`), вызывает Gemini в `spawn_blocking`, пишет `AuditReport` в состояние и в `~/.local/state/asiba/audits/<сервер>/`, шлёт событие.
4. UI: вкладка «Аудит» сервера, кнопка «отчёт» у инцидента, индикатор «ИИ анализирует» в статусбаре.
