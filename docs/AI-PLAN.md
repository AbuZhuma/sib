# ИИ-анализ в Asiba

Цель: приложение само готовит для языковой модели ровно те данные, которые нужны, вызывает её по каждому негативному событию, при запуске, на каждой вкладке и по запросу, а результат показывает рядом с данными. Провайдер — Gemini, OpenAI, Claude или OpenAI-совместимый API; включается только явным согласием пользователя.

## Принципы

1. **Детерминированный анализ делает Asiba, а не модель.** Проверки безопасности, аномалии, алерты, упавшие юниты и деплои — это код с тестами (`asiba-incidents`). Модель получает факты и готовые выводы, её работа — связать их, расставить приоритеты, объяснить причину и предложить шаги.
2. **Контекст собирается из секций.** Все данные о сервере описаны как набор секций с идентификаторами (`asiba-docgen`). Полный файл — это все секции; контекст для инцидента — только нужные. Новая секция = новый файл, регистрация в списке.
3. **Каждый негатив — инцидент.** Единый тип `Incident` в `asiba-core`. Детекторы — маленькие модули с общим трейтом. Новая причина для вызова модели = новый детектор и (при необходимости) плейбук.
4. **Плейбук связывает инцидент с моделью.** Для каждого вида инцидента: какие секции дать, какие данные дополнительно запросить с сервера (логи контейнера, journalctl юнита), какую задачу поставить.
5. **Ничего не уходит без согласия.** По умолчанию ИИ выключен. В настройках пользователь ставит галочку с текстом, что именно будет отправляться провайдеру, выбирает провайдера и указывает ключ (и URL для совместимого API). Пока `consent` не стоит, `asiba-ai` не делает сетевых запросов.
6. **Модель не блокирует UI и сбор данных.** Один воркер, очередь, один запрос за раз, кулдаун на повторные инциденты (по умолчанию 30 мин на `сервер:вид:объект`).
7. **Временные сбои провайдера гасятся сами.** Ответы 408/429/5xx и сетевые ошибки считаются временными: запрос повторяется через 3, 10 и 30 с (`asiba_ai::complete_with_retry`); если выбранная модель так и не ответила, воркер пробует запасные модели провайдера (`AiProvider::fallback_models`, для Gemini - `gemini-3.6-flash`, затем `gemini-flash-latest`) и записывает в отчёт ту, что ответила. Ошибки ключа и формата не повторяются. Если после всех попыток провайдер отвечает 429 (квота исчерпана), автоматические запросы приостанавливаются на 15 минут, ручные («Проанализировать», «Полный аудит») выполняются как обычно.

## Что отправляется

Только текст, собранный из секций `<имя>.llm.md` по плейбуку инцидента (или все секции для полного аудита), плюс вывод запросов к серверу (`docker logs`, `journalctl -u`). Пароли и ключи в этих данных не участвуют. Список секций: findings, description, system, resources, alerts, security, anomalies, services, docker, deploy, processes, ports, users, updates, logs, gpu, actions, events.

## Провайдеры

`asiba-ai::Backend` с реализациями `Gemini` (`generateContent`, `x-goog-api-key`), `OpenAi` (`/chat/completions`, `Authorization: Bearer`; тот же класс с другим `base_url` — любой совместимый API) и `Anthropic` (`/v1/messages`). Модели по умолчанию: `gemini-3.6-flash`, `gpt-5-mini`, `claude-sonnet-5`; меняются в настройках. Лимит контекста задаётся в настройках (по умолчанию 60 000 токенов); части контекста режутся по приоритету, если не влезают.

## Виды анализа и промпты

Системный промпт один: роль инженера по эксплуатации и безопасности, только факты из дампа, команды под дистрибутив сервера, ссылки на строки данных, ответ по-русски. Задача и формат ответа — из плейбука:

- **Сводка по парку** (`AuditTarget::Fleet`, при запуске и по кнопке на главной): для каждого сервера findings + description + system + alerts, серверы с критичными инцидентами первыми. Формат: Общее состояние / Требуют внимания (по срочности) / Первые шаги.
- **Инцидент** (автоматически при открытии, с уровня из настроек, кулдаун 30 мин): секции по виду инцидента плюс `docker logs` / `journalctl -u`. Формат: Причина / Доказательства / Что сделать сейчас / Как предотвратить.
- **Раздел** (`AuditScope::Section`, при первом открытии вкладки сервера - если в настройках включён автоанализ разделов и раздел отмечен в списке (`AiConfig.auto_sections`, `sections`) - и по кнопке «Проанализировать»/«Обновить»): findings + секция вкладки + смежные (например, processes + resources). Формат: Состояние / Что настораживает / Рекомендации.
- **Полный аудит** (по кнопке): все секции. Формат: Итог / Критично / Рекомендуется / Замечания.

## Плейбуки

- контейнер упал / unhealthy → `docker logs`, секции docker, resources, deploy, events;
- юнит упал → `journalctl -u`, секции services, logs, resources, events;
- деплой упал → deploy (с хвостом лога), docker, services, logs;
- аномалия / брутфорс → anomalies, security, ports, resources, events;
- проверка безопасности / обновления → security, users, ports, updates;
- ресурсы (алерты, диск, память, часы, ошибки модуля) → resources, processes, docker, services, logs;
- полный аудит → все секции, findings первым.

## Поток

1. Цикл алертов открывает инцидент (`asiba-incidents::reconcile`).
2. Если ИИ включён и `auto_audit`, движок ставит задание `Audit { scope: Incident }` в очередь воркера (`engine/src/ai/`). Кнопки «разобрать» и «Полный аудит» ставят задания вручную.
3. Отчёт появляется в состоянии сразу со статусом «в очереди» (`AuditStatus::Queued`), чтобы кнопка отзывалась мгновенно; воркер переводит его в «выполняется», а пропущенные автозадания (кулдаун, уровень, пауза по квоте) убирает из списка.
4. Воркер собирает контекст (`context::prepare`), вызывает Gemini в `spawn_blocking`, пишет `AuditReport` в состояние и в `~/.local/state/asiba/audits/<сервер>/`, шлёт событие.
5. UI: блок «ИИ-сводка по всем серверам» и «Разборы инцидентов» на главной, блок «ИИ-анализ» в сводке сервера, «ИИ-анализ раздела» на каждой вкладке, вкладка «Аудит» со всеми отчётами, кнопки «разобрать»/«отчёт» у инцидента, индикатор «ИИ анализирует» в статусбаре.
