# Asiba — техническое задание, версия 1.0

Универсальная система мониторинга Linux-серверов. Настольное приложение под Linux, написанное на Rust. Подключается к любому количеству серверов по SSH, собирает всё, что может найти, и показывает это на плотном профессиональном дашборде. Не привязана к конкретному проекту: сервер любого назначения добавляется вводом данных для входа, и приложение само определяет, какие данные на нём доступны.

---

## 1. Цели и границы

### 1.1 Цели
- Единое окно для всех серверов: список, общая картина, детали каждого.
- Безагентный сбор: на сервер ничего ставить не нужно, достаточно SSH.
- Показывать только то, что реально есть на сервере. Модуль, для которого нет данных, не отображается в UI вообще.
- Расширяемость: новый тип данных добавляется как отдельный модуль без правок остального кода.
- Живая документация: на каждый сервер ведётся файл с описанием и текущим состоянием, который приложение обновляет само.

### 1.2 Вне рамок v1
- Мобильные и веб-версии.
- Мониторинг Windows/macOS.
- Многопользовательский режим, роли, авторизация внутри приложения.
- Интеграции с внешними алертингами (Telegram, Slack, PagerDuty) — заложить интерфейс, реализовать в v2.
- Установка собственного агента на сервер — заложить как опциональный ускоритель, реализовать в v2.

### 1.3 Терминология
- **Сервер** — один хост, добавленный в приложение.
- **Модуль** — самостоятельный блок функциональности: сборщик данных + модель + виджеты UI (например, `docker`, `ports`, `deploy`).
- **Сборщик (collector)** — часть модуля, которая получает сырые данные с сервера.
- **Снимок (snapshot)** — результат одного цикла сбора модуля.
- **Сессия** — открытое SSH-соединение с сервером, переиспользуемое всеми модулями.

## 2. Технологический стек

| Слой | Решение | Обоснование |
|---|---|---|
| Язык | Rust stable (edition 2024) | требование проекта |
| Асинхронность | tokio | стандарт, много зрелых крейтов |
| SSH | russh + russh-keys | чистый Rust, без зависимости от libssh, поддержка ключей, паролей, агента |
| UI | eframe / egui | нативно, быстрое обновление в реальном времени, полностью кастомизируемый стиль |
| Графики | egui_plot | родной для egui |
| Карта | walkers | тайловая карта для egui, отметки серверов и линии пинга |
| Хранилище истории | SQLite через rusqlite (bundled) | один файл, нулевые зависимости у пользователя |
| Конфигурация | TOML через serde | читаемо руками |
| Секреты | keyring (secret-service) с fallback на зашифрованный файл (age/chacha20poly1305) | пароли и passphrase ключей не лежат в открытом виде |
| Ошибки | thiserror в библиотеках, anyhow на границе приложения | |
| Логи приложения | tracing + tracing-subscriber | |
| Уведомления | notify-rust | системные уведомления через D-Bus |
| Геолокация IP | HTTP-запрос к публичному сервису (ip-api.com или аналог), кешируется | определение положения сервера на карте |

Если в ходе разработки egui окажется недостаточно для требуемого визуального стиля, допустимая замена — iced. Решение принимается до начала работы над UI и фиксируется в `docs/DECISIONS.md`.

### 3.2 Принципы
- Зависимости направлены только внутрь: `ui → engine → modules, transport, config → core`, `app → всё`. `core` не знает ни про SSH, ни про egui.
- Модуль — это реализация трейта. Регистрация модулей происходит в одном месте (`asiba_modules::default_registry`), в реестре. Добавление модуля = новая папка + одна строка в реестре.
- Сбор данных и UI полностью разделены и общаются через каналы. UI никогда не блокируется на сети.
- Один сервер — одна долгоживущая SSH-сессия с мультиплексированием каналов. Все модули работают через неё. Переподключение автоматическое с экспоненциальной задержкой.
- Все данные с сервера получаются чтением `/proc`, `/sys` и стандартными утилитами (`ss`, `docker`, `systemctl`, `journalctl`, `ip`, `df`, `nft`/`iptables`, `fail2ban-client`). Никаких зависимостей от нестандартного ПО на сервере.
- Локальная машина мониторится тем же путём через `LocalTransport` (без SSH), интерфейс транспорта одинаковый.

### 3.3 Ключевые трейты (в `asiba-core`)

```rust
pub trait Transport: Send + Sync {
    async fn exec(&self, cmd: &str) -> Result<Output>;
    async fn read_file(&self, path: &str) -> Result<String>;
    async fn stream(&self, cmd: &str) -> Result<LineStream>;
}

pub trait Module: Send + Sync {
    fn id(&self) -> ModuleId;
    fn title(&self) -> &'static str;
    fn schedule(&self) -> Schedule;
    async fn detect(&self, t: &dyn Transport) -> Result<Availability>;
    async fn collect(&self, t: &dyn Transport, ctx: &CollectCtx) -> Result<Snapshot>;
    fn actions(&self) -> &[ActionSpec];
    async fn run_action(&self, t: &dyn Transport, action: ActionCall) -> Result<ActionResult>;
}
```

- `detect` вызывается при подключении и раз в N минут. Возвращает `Available`, `Unavailable(reason)` или `Partial(features)`. UI строится по результату: нет модуля — нет вкладки, нет виджета, нет упоминания.
- `Schedule` — интервал сбора: `Fast(1–2 с)` для живой статистики, `Normal(10–30 с)`, `Slow(1–10 мин)`, `OnDemand`.
- `Snapshot` — типизированные данные модуля плюс список порождённых событий (`Event`) и метрик для истории (`Sample`).
- Действия (`ActionSpec`) — то, что пользователь может сделать из UI: забанить IP, перезапустить сервис, убить процесс. Каждое действие подтверждается диалогом.

### 3.4 Потоки данных

```
Планировщик ──► Модуль.collect ──► Snapshot ──┬──► Состояние в памяти ──► UI
                                              ├──► Storage (история)
                                              ├──► Alerts (оценка правил)
                                              └──► Docgen (обновление файла сервера)
```

Состояние в памяти — `Arc<RwLock<AppState>>`, UI читает его на каждом кадре. Тяжёлые данные (логи, списки процессов) хранятся с ограничением по размеру.

### 3.5 Хранение

| Что | Где |
|---|---|
| Конфигурация приложения | `~/.config/asiba/config.toml` |
| Конфигурация серверов | `~/.config/asiba/servers/<name>.toml` |
| Файлы-описания серверов | `~/.config/asiba/servers/<name>.md` (путь папки настраивается, по умолчанию рядом с конфигами; можно указать папку внутри репозитория проекта) |
| Секреты | системный keyring; fallback `~/.config/asiba/secrets.enc` |
| История метрик и событий | `~/.local/share/asiba/history.db` |
| Кеш (геолокация, тайлы карты) | `~/.cache/asiba/` |
| Логи приложения | `~/.local/state/asiba/logs/` |

Хранение истории: сырые сэмплы 48 часов, поминутные агрегаты 30 дней, почасовые 1 год. Даунсэмплинг фоновой задачей. Размер базы ограничен настройкой.

## 4. Серверы

### 4.1 Добавление сервера
Форма с полями:
- **Имя** (обязательно, уникально, латиница/цифры/дефис) — становится именем файлов.
- **Хост** (IP или домен), **порт** (по умолчанию 22), **пользователь**.
- **Способ входа**: приватный ключ (путь к файлу или вставка текста, опциональная passphrase), пароль, или **авто** — использовать `~/.ssh/config`, ssh-agent и стандартные ключи `~/.ssh/id_*`. Если ничего не указано, выбирается «авто».
- **Jump host** (опционально) — подключение через промежуточный сервер.
- **sudo**: без sudo / sudo без пароля / sudo с паролем. Часть данных (nftables, journal других пользователей, docker без группы) требует прав.
- **Описание**: название проекта, назначение сервера, свободный текст, теги, окружение (prod/stage/dev), ответственный, ссылки.
- **Папка для файла сервера** — если отличается от глобальной.

Перед сохранением — кнопка «Проверить подключение»: показывает, что удалось подключиться, версию ОС и результат `detect` всех модулей (какие модули будут активны).

### 4.2 Карточка сервера в списке
- Имя, хост, окружение, теги.
- Статус: online / offline / connecting / degraded (есть активные алерты).
- Мини-показатели: CPU %, RAM %, диск %, входящая/исходящая скорость, пинг, uptime.
- Количество активных алертов по уровням.
- Мини-график нагрузки за последний час (sparkline).
- Список доступных модулей в виде компактных значков.

Клик — переход в детали. Список сортируется и фильтруется по имени, статусу, окружению, тегам.

### 4.3 Файл сервера (`<name>.md`)
Генерируется приложением и обновляется после каждого цикла сбора модулей `services`, `docker`, `ports` (не чаще раза в минуту, только при изменениях). Структура:

```
# neo

<!-- notes:start -->
(ручной блок, приложение его не трогает)
<!-- notes:end -->

## Описание
Проект, назначение, окружение, теги, ответственный — из конфигурации.

## Система
ОС, ядро, CPU, RAM, диски, IP-адреса, расположение, uptime.

## Процессы
Топ процессов по CPU и памяти.

## Сервисы systemd
Активные, упавшие, отключённые (только не-системные и упавшие системные).

## Docker
Контейнеры, образы, сети, тома, compose-проекты.

## Порты
Порт, протокол, процесс, проект, доступность снаружи.

## Деплой
Способ деплоя, последний деплой, статус.

## Последние проблемы
Последние 20 событий уровня warning и выше.

_Обновлено: 2026-09-14 13:10:00_
```

Блок между `notes:start` / `notes:end` сохраняется при перезаписи. Всё остальное перегенерируется. Файл переименовывается при переименовании сервера, удаляется при удалении сервера (с подтверждением).

## 5. Модули v1

Для каждого модуля: условие доступности, что собирает, что показывает, какие события порождает, какие действия даёт.

### 5.1 `system` — базовая информация
- Доступность: всегда.
- Сбор: hostname, дистрибутив, версия ядра, архитектура, uptime, load average, модель CPU, число ядер, объём RAM, виртуализация (`systemd-detect-virt`), часовой пояс, время на сервере и расхождение с локальным.
- UI: шапка страницы сервера.

### 5.2 `cpu`
- Доступность: всегда.
- Сбор (Fast): загрузка общая и по ядрам (`/proc/stat`), user/system/iowait/steal, частота, температура (`/sys/class/thermal`, `hwmon`), throttling.
- UI: живой график загрузки, сетка ядер, температура.
- События: загрузка > порога N минут, iowait > порога, температура > порога.

### 5.3 `memory`
- Доступность: всегда.
- Сбор (Fast): `/proc/meminfo` — total/used/available/cached/buffers, swap, `/proc/pressure/memory` (PSI) если есть, OOM-события из dmesg/journal.
- UI: график, разбивка по типам, PSI.
- События: available < порога, swap используется активно, OOM kill.

### 5.4 `disk`
- Доступность: всегда.
- Сбор (Normal): файловые системы (`df`), inode, точки монтирования; (Fast) IO по устройствам (`/proc/diskstats`): чтение/запись, IOPS, utilization; PSI io; SMART через `smartctl` если установлен и есть права.
- UI: таблица ФС с прогресс-барами, графики IO, SMART-статус.
- События: заполнение > порога, прогноз заполнения < N дней (линейная экстраполяция), ошибки SMART, ошибки IO в dmesg.

### 5.5 `network`
- Доступность: всегда.
- Сбор (Fast): интерфейсы, адреса, скорость линка, rx/tx байты и пакеты, ошибки, drops (`/proc/net/dev`, `ip -j`); число соединений по состояниям (`ss -s`); публичный IP; шлюз, DNS.
- Пинг: приложение само пингует сервер с локальной машины (ICMP или TCP-connect к SSH-порту, если нет прав на raw socket) — задержка, потери, джиттер, история.
- Геолокация: по публичному IP через внешний сервис, кешируется, можно переопределить вручную (страна, город, координаты, провайдер/датацентр).
- UI: графики скорости по интерфейсам, таблица интерфейсов, пинг, карта с положением сервера и линией от локальной машины с подписью задержки.
- События: линк упал, ошибки/drops растут, пинг > порога, потери пакетов, смена публичного IP.

### 5.6 `processes`
- Доступность: всегда.
- Сбор (Fast): все процессы из `/proc/[pid]`: PID, PPID, пользователь, команда, состояние, CPU %, RSS, VSZ, потоки, открытые файлы (при наличии прав), IO чтение/запись (`/proc/[pid]/io`), сетевые соединения на процесс (по `ss -p`), время запуска, cgroup (для привязки к контейнеру/сервису).
- UI: таблица с сортировкой по любому столбцу, поиск, дерево процессов, топ-N по CPU / памяти / IO / сети, детальная панель процесса. Столбцы «что именно потребляет»: CPU, RAM, disk read/write, net rx/tx, соединения.
- События: новый процесс с высоким потреблением, зомби, процесс исчез из списка «наблюдаемых».
- Действия: SIGTERM, SIGKILL, отметить процесс как «наблюдаемый».

### 5.7 `services` — systemd
- Доступность: есть `systemctl`.
- Сбор (Normal): все юниты (`systemctl list-units --all -o json`), состояние, время запуска, число рестартов, `failed` юниты, таймеры, юниты с `Restart=` которые циклично перезапускаются.
- UI: таблица, фильтр «только не системные», «только проблемные», панель юнита с последними строками журнала.
- События: юнит перешёл в failed, циклический перезапуск, таймер не отработал.
- Действия: start / stop / restart, показать журнал.

### 5.8 `docker`
- Доступность: есть `docker` и доступ к сокету (напрямую или через sudo). Если есть `podman` — работать с ним через тот же интерфейс.
- Сбор (Normal): контейнеры (все, включая остановленные): имя, образ, состояние, health, время работы, число рестартов, порты, сети, тома, compose-проект и сервис (из labels), политика рестарта. Образы: размер, dangling. Тома, сети. Использование диска (`docker system df`). (Fast) `docker stats`: CPU, память/лимит, net rx/tx, block IO по каждому контейнеру.
- UI: карточки/таблица контейнеров, группировка по compose-проекту, живые графики на контейнер, просмотр логов с хвостом и фильтром, inspect в виде дерева.
- События: контейнер упал / unhealthy / рестарт-луп, exit code ≠ 0, память у лимита, образ dangling > N.
- Действия: start / stop / restart, показать логи, удалить остановленный контейнер.

### 5.9 `logs` — ошибки и проблемы
- Доступность: есть `journalctl` или читаемые `/var/log/*`.
- Сбор (Normal): `journalctl -p warning..emerg` за окно с последнего сбора, `dmesg` уровня err и выше, сбои аутентификации из journal/`auth.log`, сегфолты, OOM, ошибки ФС, ошибки сети. Группировка одинаковых сообщений с подсчётом.
- UI: лента с фильтром по уровню, юниту, тексту, времени; счётчики за час/сутки; группировка повторов.
- События: всплеск ошибок (> N за минуту), новая уникальная ошибка уровня crit+.

### 5.10 `ports`
- Доступность: есть `ss` или `netstat`.
- Сбор (Normal): все слушающие сокеты TCP/UDP (`ss -tulpnH`): порт, адрес привязки (0.0.0.0 / 127.0.0.1 / конкретный), процесс, пользователь, проект. Правила файрвола (`nft list ruleset -j`, `iptables-save`, `ufw status`) — какие порты открыты снаружи. Установленные соединения по портам: число, топ адресов.
- Проверка снаружи: приложение с локальной машины делает TCP-connect к каждому слушающему порту на публичном адресе — реально ли порт доступен извне.
- UI: таблица портов с колонками «слушает», «процесс», «файрвол», «доступен снаружи», «соединений»; подсветка публично открытых портов без файрвола.
- События: новый слушающий порт, порт стал недоступен, порт, который слушает 0.0.0.0 и не защищён файрволом.

### 5.11 `security`
- Доступность: всегда (объём зависит от прав и наличия `fail2ban`, `nft`/`iptables`/`ufw`).
- Сбор (Normal): неудачные входы по SSH (адрес, пользователь, число), успешные входы, sudo-вызовы, статус fail2ban и его джейлы с забаненными IP, текущий список забаненных приложением IP, изменения в `/etc/passwd`/`sudoers` (по хешу), настройки sshd (пароли разрешены? root разрешён?), `listening` на 0.0.0.0 без файрвола (из `ports`).
- UI: сводка «уровень защиты» с чеклистом, таблица атакующих IP (страна по геолокации, число попыток, первый/последний раз), список банов.
- События: брутфорс (> N неудач с одного IP за M минут), успешный вход с нового IP, изменение sudoers/passwd, root-вход.
- Действия: **забанить IP** (на N часов или навсегда) — через fail2ban если есть, иначе через nftables set, иначе iptables, иначе ufw; **разбанить**; бан прямо из таблицы соединений, атакующих IP или ленты аномалий. Список банов приложения хранится в конфигурации сервера и восстанавливается после перезагрузки сервера при подключении (опционально).

### 5.12 `anomalies` — аномалии и DDoS
- Доступность: всегда (работает поверх данных других модулей).
- Логика: для ключевых метрик (pps, bps, число соединений, SYN_RECV, новых соединений в секунду, CPU, load, число процессов, ошибки в журнале, неудачные логины) держится скользящая базовая линия (среднее и отклонение за 24 ч с учётом времени суток). Отклонение > k·σ — аномалия. Дополнительно фиксированные признаки DDoS: SYN_RECV > порога, соединений с одного IP > порога, pps > порога, топ-10 IP дают > X% трафика.
- Сбор (Fast): `ss -tan` агрегация по состоянию и удалённому адресу, счётчики `/proc/net/netstat` и `/proc/net/snmp` (SYN cookies, ListenDrops, ListenOverflows), conntrack если доступен.
- UI: лента аномалий с уровнем, описанием, графиком метрики «до/во время», подозрительными IP и кнопкой бана рядом с каждым; индикатор «сейчас идёт атака» в шапке сервера и на главной.
- События: каждая аномалия — событие с уровнем warning/critical.

### 5.13 `deploy` — отслеживание деплоя
- Доступность: обнаружен хотя бы один источник деплоя. Иначе модуль полностью скрыт.
- Источники (адаптеры, каждый — отдельный файл):
  - **docker compose**: события `docker events` (create/start/die/pull), `docker compose ps` — стадии pull → create → start → healthy.
  - **systemd**: юнит с именем по маске `deploy*` или указанный вручную — статус, журнал.
  - **лог-файл**: путь к логу деплоя, задаётся вручную в конфигурации сервера, с набором регулярных выражений для стадий и ошибок (шаблон для стандартных выводов `docker compose up`, `npm run build`, `cargo build`, `pip install`, `systemctl restart`).
  - **self-hosted CI runner** (GitHub Actions / GitLab Runner): по наличию процесса раннера и его рабочей папки — текущий job, стадия, лог.
- Данные: список деплоев (история), для каждого: проект, источник, начало/конец, стадии с временем и статусом, текущая стадия, строка с ошибкой и контекст вокруг неё (±20 строк), итог success/failed/in-progress.
- UI: таймлайн стадий (горизонтальный, стадии как блоки), текущий деплой с живым логом, история с фильтром, при ошибке — красный блок с местом ошибки и переходом к полному логу.
- События: деплой начался, завершился, упал (с указанием стадии).

### 5.14 `projects` — убран
Модуль и вкладка «Проекты» удалены 2026-09-15 (см. DECISIONS.md): сущность «проект» оказалась не нужна, связи контейнеров и юнитов видны в своих разделах.

### 5.15 `users`
- Доступность: всегда.
- Сбор (Normal): активные сессии (`who`, `w`), история входов (`last`), пользователи с shell, пользователи в sudo/wheel, ключи в `authorized_keys` (число и комментарии).
- UI: таблица сессий, история.
- События: новая сессия, новый пользователь, новый ключ в authorized_keys.

### 5.16 `updates`
- Доступность: найден один из `apt`, `dnf`, `yum`, `pacman`, `zypper`, `apk`.
- Сбор (Slow): число доступных обновлений, из них security, нужна ли перезагрузка (`/var/run/reboot-required`, `needs-restarting`), дата последнего обновления.
- UI: блок в сводке сервера.
- События: security-обновления > 0, перезагрузка требуется > N дней.

### 5.17 `gpu`
- Доступность: есть `nvidia-smi` или `/sys/class/drm/card*/device/gpu_busy_percent` (AMD).
- Сбор (Fast): загрузка, память, температура, мощность, процессы на GPU.
- UI: графики.
- События: температура/память > порога.

### 5.18 `git` — репозитории на сервере
- Доступность: установлен `git` и найден хотя бы один `.git` в стандартных папках проектов (`/opt /srv /var/www /home/* /root /app /docker /data`, глубина 3). Иначе модуль скрыт.
- Сбор (Normal): по каждому репозиторию — путь, ветка (или detached HEAD), HEAD, remote `origin`, расхождение с upstream (ahead/behind), незакоммиченные файлы (`status --porcelain`), число stash, список веток, последние теги, последние 100 коммитов (хеш, автор, время, refs, сообщение).
- Запрос «вся история»: полный `git log` репозитория (до 2000 коммитов) в панель просмотра.
- UI: список репозиториев, у каждого — строка состояния (ветка, хеш, ahead/behind, изменения, stash, remote), незакоммиченные файлы, ветки, теги, таблица коммитов.
- События: новый коммит в репозитории (HEAD сменился), переключение ветки.

### 5.19 Пороги и настройки модулей
Каждый модуль имеет настройки по умолчанию и переопределение на уровне сервера (в `<name>.toml`): интервалы, пороги, включён/выключен, пути для сканирования. Модуль можно выключить вручную даже если он доступен.

### 6.2 Главная (обзор)
- Сводные плитки: серверов всего / online / с проблемами; суммарные CPU, RAM, диск по всему парку; суммарный трафик; активных алертов.

## 7. Визуальный стиль

- Тема по умолчанию — тёмно-серая. Светло-серая — вторая тема, обе на одних токенах.
- Палитра (тёмная):
  - фон окна `#1c1e21`, фон панелей `#24272b`, фон приподнятых элементов `#2c3035`
  - границы `#3a3f45`, границы активных `#5a616a`
  - текст основной `#d7dadf`, вторичный `#8b929a`, приглушённый `#5f666e`
  - акцент `#4f8cc9` (только для выделения активного, ссылок, курсора графика)
  - статусы: ok `#3f9d5a`, warning `#d0a13a`, critical `#c94f4f`, info `#5a8fd0`, offline `#6b7076`
- Радиус скругления 2 px везде. Никаких теней. Границы 1 px, чёткие.
- Шрифты: Inter (или системный sans) для текста, JetBrains Mono для чисел, кодов, логов, адресов, портов. Все числовые столбцы — моноширинные, выровнены по правому краю.
- Графики: одна линия — один цвет из ограниченной палитры серо-синих оттенков; заливка под линией 10 % прозрачности; сетка тонкая; подписи компактные.
- Плотность: строка таблицы 24 px, заголовки панелей 28 px. Информация важнее пустого места.
- Иконки — монохромные линейные, один набор (Lucide или Phosphor, растеризованные в атлас).
- Все интерактивные элементы имеют состояния hover/active/disabled, видимые, но сдержанные.
- Обновление в реальном времени без мерцания: значения меняются на месте, графики сдвигаются плавно.
- Все размеры и цвета — в одном файле темы; компоненты не содержат «магических» значений.

## 8. Действия и безопасность

- Каждое действие (бан, kill, restart, stop) — только через диалог подтверждения с указанием сервера и цели. Опасные (kill -9, stop контейнера в prod) — с вводом имени сервера.
- Журнал действий: кто/что/когда/результат, хранится в базе и показывается в настройках.
- Секреты: пароли и passphrase — только в keyring или в зашифрованном файле с мастер-паролем; в TOML не попадают. Приватные ключи, вставленные текстом, сохраняются в `~/.config/asiba/keys/<name>` с правами 0600.
- Приложение не хранит команды с секретами в истории и не логирует их.
- Все команды на сервере — только чтение, кроме явно объявленных действий. Список команд каждого модуля документируется в `MODULE_GUIDE.md`.
- Host key сервера проверяется через `~/.ssh/known_hosts`; при первом подключении — диалог с отпечатком.

## 9. Поведение при сбоях

- Сервер недоступен: карточка переходит в offline, последние известные данные остаются на экране с пометкой «данные на HH:MM», переподключение по расписанию 5 с → 10 с → 30 с → 60 с.
- Модуль упал (ошибка парсинга, команда не найдена): модуль помечается degraded, показывается причина в его виджете, остальные модули продолжают работать. После 3 подряд ошибок — повторный `detect`.
- Внешний сервис геолокации недоступен: используется кеш или ручные координаты, UI не ломается.
- Нет прав на что-то: модуль работает частично и показывает, чего именно не хватает и как исправить (например «добавьте пользователя в группу docker»).

## 10. Производительность

- Сбор Fast-модулей на сервере не должен создавать заметной нагрузки: один вызов — одна команда-скрипт, читающая всё нужное из `/proc` за проход (не десятки отдельных `exec`).
- Приложение при 10 серверах: < 300 МБ RAM, < 5 % CPU на простое, 60 FPS в UI при открытых графиках.
- Парсинг вывода — потоковый, без загрузки гигабайтных логов в память: хвост логов ограничен N строк.
- Запись в SQLite батчами раз в N секунд, в отдельной задаче.

## 12. План реализации

Этапы идут последовательно, каждый заканчивается рабочим приложением.

1. **Каркас** — workspace, core-трейты, транспорт SSH + Local, конфигурация, реестр модулей, пустое окно с темой и навигацией, добавление сервера, проверка подключения.
2. **Базовые модули** — system, cpu, memory, disk, network (без карты), processes. Карточки серверов, страница сервера со сводкой и вкладками, живые графики. Хранилище истории.
3. **Инфраструктурные модули** — services, docker, ports, logs, users, updates. Файл сервера (docgen). Модуль projects.
4. **Безопасность** — security, anomalies, действия (бан IP, kill, restart), журнал действий, алерты и уведомления.
5. **Деплой и карта** — модуль deploy со всеми адаптерами, геолокация, карта, пинг.
6. **Полировка** — главная страница целиком, раскладка виджетов, светлая тема, gpu, настройки, документация, тесты на всех фикстурах.
