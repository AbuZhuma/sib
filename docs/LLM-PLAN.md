# Локальная ЛЛМ в Asiba — план

Цель: приложение само готовит для локальной модели ровно те данные, которые нужны, вызывает её по каждому негативному событию и по запросу, а результат показывает как аудит. Ничего не покидает машину: модель крутится в `llama-server` на `127.0.0.1`, файл модели пользователь кладёт сам.

## Принципы

1. **Детерминированный анализ делает Asiba, а не модель.** Проверки безопасности, аномалии, алерты, упавшие юниты и деплои — это код с тестами. Модель получает факты и готовые выводы, её работа — связать их, расставить приоритеты, объяснить причину и предложить шаги. Так даже модель на 1–3 ГБ даёт пользу и почти не выдумывает.
2. **Контекст собирается из секций.** Все данные о сервере описаны как набор секций с идентификаторами. Полный файл — это все секции; контекст для инцидента — только нужные. Новая секция = новый файл в `asiba-docgen`, регистрация в списке.
3. **Каждый негатив — инцидент.** Единый тип `Incident` в `asiba-core`. Детекторы — маленькие модули с общим трейтом. Добавить новую причину для вызова модели = добавить детектор и (при необходимости) плейбук.
4. **Плейбук связывает инцидент с моделью.** Для каждого вида инцидента: какие секции дать, какие данные дополнительно запросить с сервера (логи контейнера, journalctl юнита), какую задачу поставить. Новый вид инцидента без плейбука использует плейбук по умолчанию.
5. **Только localhost.** В крейте `asiba-llm` нет адресов кроме `127.0.0.1`, нет автоскачивания. Это правило записано в DECISIONS.md.
6. **Модель никогда не блокирует UI и сбор данных.** Один воркер, очередь, один запрос за раз, кулдаун на повторные инциденты.

## Модель и рантайм

- Рантайм: `llama-server` из пакета Fedora `llama-cpp` (`sudo dnf install llama-cpp`), запускается самим приложением: `llama-server -m <gguf> --host 127.0.0.1 --port <свободный> -c 8192 -t <потоки> --no-webui`. Общение — HTTP `/v1/chat/completions` через `ureq`. Гасится после простоя, чтобы освободить память.
- Модель по умолчанию: **Qwen3-4B-Instruct, GGUF Q4_K_M** (~2.5 ГБ на диске, ~3 ГБ RAM с контекстом 8k, ~6–9 ток/с на CPU без GPU). Это минимальный размер, на котором ответы реально полезны. Запасной вариант для слабых машин — Qwen2.5-1.5B-Instruct Q4_K_M (~1.2 ГБ RAM). Путь к любому GGUF задаётся в настройках.
- Бюджет контекста: окно 8192 токена, из них до 6000 на данные, остальное — промпт и ответ. Оценка токенов — по символам (÷ 3.5 для смешанного текста), секции обрезаются по приоритету.

## Секции данных (`asiba-docgen`)

Каждая секция реализует один трейт:

```
trait Section {
    fn id(&self) -> SectionId;
    fn is_available(&self, server: &ServerState) -> bool;
    fn human(&self, out: &mut String, server: &ServerState);   // русский markdown
    fn llm(&self, out: &mut String, server: &ServerState);     // английский, key: value, списки ограничены
}
```

Список секций: `description`, `system`, `resources` (CPU/RAM/диск/сеть — текущие значения и сводка за час и сутки), `processes`, `projects`, `services`, `docker`, `ports`, `deploy`, `users`, `updates`, `logs`, `security`, `anomalies`, `gpu`, `alerts`, `actions`, `events`, `findings` (сводка всех проблем, найденных Asiba, с приоритетами).

Два файла в папке серверов:
- `<имя>.md` — для человека, все секции, блок `notes` сохраняется.
- `<имя>.llm.md` — для модели, все секции в компактном виде, стабильный порядок, без оформления.

Обновление: после цикла любого модуля, не чаще раза в 10 с, только если содержимое изменилось.

## Инциденты (`asiba-core` + `asiba-alerts`)

```
struct Incident {
    id, server, kind: IncidentKind, severity, at,
    subject: String,            // имя юнита, контейнера, IP, метрика
    summary: String,            // одна строка для событий и уведомлений
    evidence: Vec<String>,      // строки-факты
    sections: Vec<SectionId>,   // что показать модели
}
enum IncidentKind { Alert, Anomaly, DeployFailed, UnitFailed, ContainerDied,
                    BruteForce, SecurityDrop, ServerOffline, ModuleError, DiskFull, ... }
```

Детекторы (`asiba-alerts/src/incidents/<kind>.rs`), трейт `Detector { fn detect(&self, previous, current) -> Vec<Incident> }`. Список детекторов — один массив в `incidents/mod.rs`. Движок прогоняет детекторы после каждого сбора, новые инциденты кладёт в `AppState.incidents`, шлёт `EngineEvent::Incident`, событие в журнал, уведомление на рабочий стол по настройке. Инциденты полезны и без модели — они видны в UI как отдельный список.

## Плейбуки и промпты (`asiba-llm`)

```
struct Playbook {
    kind: IncidentKind,
    sections: &'static [SectionId],           // базовый контекст
    queries: fn(&Incident) -> Vec<QueryRequest>, // что дополнительно спросить у сервера
    task: &'static str,                          // формулировка задачи для модели
}
```

Примеры:
- `ContainerDied` → секции `docker`, `projects`, `resources`; запросы `docker logs --tail 200 <name>`, `docker inspect` (состояние, код выхода); задача: объяснить причину падения по логам и предложить исправление.
- `UnitFailed` → `services`, `resources`, `logs`; запрос `journalctl -u <unit> -n 200`; задача: причина и шаги.
- `DeployFailed` → `deploy`, `projects`, `docker`, `services`, логи деплоя; задача: на каком шаге упало, почему, что проверить.
- `Anomaly`/`BruteForce` → `anomalies`, `security`, `ports`, `findings`; задача: это атака или нагрузка, что заблокировать, какие правила.
- `Alert` (ресурсы) → `resources`, `processes`, `docker`, `services`; задача: кто потребляет и что с этим делать.
- `Full audit` (по кнопке) → все секции с приоритетами `findings` > `security` > `anomalies` > `services` > … ; задача: полный аудит: критично / рекомендуется / замечания.

Сборка контекста: `ContextBuilder::new(budget).sections(...).extra(запросы).build()` — режет по приоритету и лимиту строк на секцию. Промпт: системная роль (Linux ops/security auditor, только факты из данных, если данных нет — сказать об этом, ответ на английском, фиксированные заголовки `Summary / Root cause / Critical / Recommended / Notes`), затем контекст, затем задача.

Бэкенд: `trait Backend { fn complete(&self, request: &Completion) -> Result<String, LlmError> }`, реализация `LlamaServer` (запуск процесса, ожидание `/health`, запрос, остановка по простою). Мок-бэкенд для тестов.

## Движок (`asiba-engine/src/llm.rs`)

- `Command::Audit { server, scope: Full | Incident(id) }`, `EngineEvent::AuditFinished(report_id)`, `EngineEvent::AuditFailed`.
- Воркер: очередь заданий, один за раз; инцидент с тем же `kind + subject` не отправляется повторно в течение кулдауна (30 мин по умолчанию); настройка «автоаудит по инцидентам с уровня N».
- Дополнительные запросы к серверу выполняются через `Module::query` (все команды описаны в MODULE_GUIDE.md).
- Отчёт `AuditReport { id, server, scope, at, model, context_tokens, text }` в `AppState.audits` и в файле `~/.local/state/asiba/audits/<сервер>/<время>-<вид>.md`.

## UI

- Настройки → «Локальная модель»: включена (по умолчанию выключена), путь к GGUF, путь к `llama-server` (по умолчанию из PATH), потоки, автоаудит по инцидентам, кулдаун, простой до выгрузки.
- Страница сервера → вкладка «Аудит»: кнопка «Полный аудит», список отчётов, текст отчёта; в блоке инцидента кнопка «Разобрать» (запуск плейбука вручную).
- Статусбар: «модель: думает…» / «модель выгружена».
- Главная: блок «Инциденты» с последними и ссылкой на отчёт, если он есть.
- Уведомление на рабочий стол «Аудит готов: <сервер> — <summary>».

## Этапы

1. **Секции и два файла.** Трейт `Section`, перенос существующих секций, новые секции для всех модулей, `<имя>.llm.md`, запись раз в 10 с по изменению. Тесты: снимок → ожидаемый markdown для каждой секции в обоих форматах.
2. **Инциденты.** Тип в core, детекторы (alert, anomaly, deploy, unit, container, brute-force, security-drop, offline, module-error), список в состоянии, события, уведомления, блок на главной и в сводке сервера. Тесты детекторов на снимках.
3. **`asiba-llm`.** Backend + LlamaServer, ContextBuilder с бюджетом, плейбуки, промпты. Записи в DECISIONS.md. Тесты на мок-бэкенде: сборка контекста, обрезание, выбор плейбука.
4. **Движок.** Воркер аудитов, команды и события, кулдаун, запросы данных, хранение отчётов, настройки в конфиге.
5. **UI.** Настройки, вкладка «Аудит», статусбар, уведомления, кнопка «Разобрать» у инцидента.
6. **Калибровка.** Прогон на реальных инцидентах локального сервера (уронить контейнер, юнит, деплой), сравнение Qwen3-4B и Qwen2.5-1.5B, доводка промптов и лимитов секций. Документация в README.
